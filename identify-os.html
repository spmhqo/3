Identify The Operating System

Identify The Operating System Prompt

Prompt:
নীচে একটি Issue/Problem দেওয়া হবে। আপনার কাজ হলো সেই Issue/Problem-এর দৃশ্যমান ফলাফল বা surface-level description-এর নিচে কাজ করা actual Operating System বা অন্তর্নিহিত ব্যবস্থাটি শনাক্ত, reconstruct এবং সুসংগঠিতভাবে ব্যাখ্যা করা।

আপনাকে অবশ্যই নীচে দেওয়া Operating System-এর সংজ্ঞা এবং তিন-অঙ্গের কাঠামো কঠোরভাবে অনুসরণ করতে হবে।

OPERATING SYSTEM — LOCKED DEFINITION

যে underlying Method + Architecture + Operating Rules-এর মাধ্যমে কোনও issue তৈরি, পরিচালিত বা পুনরুৎপাদিত হয়—সেটাই সেই issue-র Operating System বা অন্তর্নিহিত ব্যবস্থা।

অন্তর্নিহিত ব্যবস্থা (দৃশ্যমান ফলাফলের নিচে থাকা সম্পূর্ণ system) হলো—

কর্মসম্পাদন-পদ্ধতি (Method): যে পদ্ধতিতে কোনও কাজ বা ঘটনা ঘটে বা সম্পন্ন হয়।

কর্মসম্পাদন-যন্ত্রব্যবস্থা (Architecture): যে দেহ, উপকরণ, যন্ত্র ও গঠনের মাধ্যমে কোনও কাজ বা ঘটনা ঘটে বা সম্পন্ন হয়।

পরিচালন-নিয়ম (Operating Rules): যে নিয়ম বা সূত্র মেনে কর্মসম্পাদন-পদ্ধতি ও কর্মসম্পাদন-যন্ত্রব্যবস্থা নিজেদের কাজ করে।

অতএব:

Operating System = Method + Architecture + Operating Rules

Method = কীভাবে কাজটি ঘটে
Architecture = কী দিয়ে/কোন machinery-র মাধ্যমে ঘটে
Operating Rules = কোন নিয়মে Method ও Architecture কাজ করে

NON-NEGOTIABLE STRUCTURAL RULE

Issue-এর Operating System একটি CLOSED THREE-COMPONENT MODEL।

Operating System-এর মধ্যে এবং শুধুমাত্র এর মধ্যে থাকবে:

1. Method
2. Architecture
3. Operating Rules

কোনও fourth component তৈরি, যোগ, নামকরণ বা প্রস্তাব করা যাবে না।

Cause, trigger, symptom, consequence, outcome, objective, behaviour, context, environment, condition, motivation, intention, belief, resource, constraint, feedback, factor, principle, mechanism, process, structure, relationship, remedy বা অন্য কোনও concept-কে Operating System-এর আলাদা বা চতুর্থ component হিসেবে প্রতিষ্ঠা করা যাবে না।

এই ধরনের কোনও concept analysis-এ প্রয়োজন হলে তা কেবল Method, Architecture অথবা Operating Rules-এর ভিতরে তার যথাযথ জায়গায় ব্যাখ্যা করা যাবে—কিন্তু আলাদা component হিসেবে নয়।

বিশেষ করে “Mechanism” শব্দটি Method-এর বিকল্প বা চতুর্থ component হিসেবে ব্যবহার করবেন না, যদি না তা স্পষ্টভাবে Method-এর কার্যপ্রণালী বোঝাতে ব্যবহৃত হয়।

ANALYSIS RULES

1. প্রথমে Issue-টির surface-level manifestation শনাক্ত করুন।

অর্থাৎ বাইরে থেকে কী দেখা যাচ্ছে, কী ঘটছে বা কী সমস্যা হিসেবে অনুভূত হচ্ছে—সংক্ষেপে তা বলুন।

Surface manifestation নিজে Operating System নয়।

2. তারপর surface-এর নিচে গিয়ে অনুসন্ধান করুন:

“এই Issue-টি তৈরি, পরিচালিত বা পুনরুৎপাদিত হওয়ার জন্য ভিতরে আসলে কীভাবে কাজটি ঘটছে?”

3. এরপর Operating System-কে অবশ্যই এই তিনটি এবং শুধুমাত্র এই তিনটি component-এ reconstruct করুন।

A. METHOD — কর্মসম্পাদন-পদ্ধতি

নির্ধারণ করুন:

* কোন কাজ বা কার্যপ্রবাহের মাধ্যমে Issue-টি তৈরি/পরিচালিত/পুনরুৎপাদিত হয়?
* কাজটি কীভাবে ঘটে?
* কীভাবে একটি step থেকে পরবর্তী step-এ যায়?
* কোন কার্যপ্রক্রিয়ার মাধ্যমে observable result তৈরি হয়?

এখানে focus থাকবে:

কীভাবে কাজটি ঘটে?

Method-এর মধ্যে Architecture বা Operating Rules-কে মিশিয়ে ফেলবেন না।

B. ARCHITECTURE — কর্মসম্পাদন-যন্ত্রব্যবস্থা

নির্ধারণ করুন:

* কোন দেহ, উপকরণ, যন্ত্র, component বা গঠনের মাধ্যমে Method-টি কাজ করে?
* এই machinery বা structure-এর কোন অংশ কী ভূমিকা পালন করে?
* কোন arrangement বা configuration Method-টিকে কাজ করার সুযোগ দেয়?

এখানে focus থাকবে:

কী দিয়ে বা কোন machinery-র মাধ্যমে কাজটি ঘটে?

Architecture-এর মধ্যে Method বা Operating Rules-কে মিশিয়ে ফেলবেন না।

C. OPERATING RULES — পরিচালন-নিয়ম

নির্ধারণ করুন:

* কোন নিয়ম বা সূত্র মেনে Method কাজ করে?
* কোন নিয়ম বা সূত্র মেনে Architecture-এর বিভিন্ন অংশ নিজেদের কাজ করে?
* কোন নিয়ম Method ও Architecture-এর operation-কে নির্দিষ্টভাবে govern করে?

এখানে focus থাকবে:

কোন নিয়মে Method ও Architecture কাজ করে?

Operating Rules-এর মধ্যে আলাদা কোনও fourth component তৈরি করবেন না।

THREE-COMPONENT INTEGRATION

তিনটি component আলাদাভাবে শনাক্ত করার পরে দেখান কীভাবে তারা একসঙ্গে কাজ করে।

অর্থাৎ:

Architecture কী machinery বা structure প্রদান করছে,
Method সেই machinery/structure-এর মাধ্যমে কীভাবে কাজটি ঘটাচ্ছে,
এবং Operating Rules কোন নিয়মে Method ও Architecture-কে operate করাচ্ছে—

এই সম্পর্কটি ব্যাখ্যা করুন।

তিনটির interaction-ই Issue-এর Operating System।

তিনটির বাইরে কোনও আলাদা “system component” নির্ধারণ করবেন না।

IMPORTANT DISTINCTIONS

নিচের বিষয়গুলিকে Operating System-এর component-এর সঙ্গে গুলিয়ে ফেলবেন না:

Symptom ≠ Operating System

Visible Result ≠ Operating System

Cause ≠ Operating System

Trigger ≠ Operating System

Consequence ≠ Operating System

Behaviour ≠ Operating System

Remedy ≠ Operating System

Objective ≠ Operating System

Context ≠ Operating System

এই বিষয়গুলির কোনওটি Method, Architecture বা Operating Rules-এর অংশ হিসেবে প্রমাণিত হলে সংশ্লিষ্ট component-এর ভিতরে ব্যাখ্যা করা যেতে পারে। কিন্তু এগুলিকে আলাদা component বানানো যাবে না।

NO FORCED CAUSAL CHAIN

Method → Architecture → Operating Rules-কে একটি বাধ্যতামূলক chronological sequence হিসেবে ধরে নেবেন না।

এগুলি Operating System-এর তিনটি constituent component।

Issue অনুযায়ী এদের পারস্পরিক relationship যেভাবে বাস্তবে কাজ করে, সেভাবেই ব্যাখ্যা করুন।

যদি তিনটির মধ্যে কোনও একটি অন্যটির operation-এর prerequisite হয়, সেটি ব্যাখ্যা করুন; কিন্তু সেই relationship-কে নতুন component হিসেবে নাম দেবেন না।

EVIDENCE AND INFERENCE

Operating System reconstruct করার সময়:

* যা Issue-এর তথ্য থেকে সরাসরি প্রতিষ্ঠিত, তা fact হিসেবে বলুন।
* যা available information থেকে যুক্তিসঙ্গতভাবে infer করা হচ্ছে, তাকে inference হিসেবে চিহ্নিত করুন।
* যা নির্ধারণ করার মতো তথ্য নেই, তা অনুমান করে পূরণ করবেন না।
* পর্যাপ্ত তথ্য না থাকলে সংশ্লিষ্ট component-এর অনিশ্চয়তা স্পষ্টভাবে জানান।
* কোনও plausible interpretation-কে established fact হিসেবে উপস্থাপন করবেন না।

একাধিক plausible Operating System model সম্ভব হলে প্রতিটি model-কে একই তিন-component framework-এ দেখান এবং কোন তথ্যের ভিত্তিতে কোন interpretation তৈরি হচ্ছে তা ব্যাখ্যা করুন।

FINAL DISCIPLINE

পুরো analysis জুড়ে মনে রাখুন:

Operating System = Method + Architecture + Operating Rules

এটি একটি CLOSED THREE-COMPONENT MODEL।

কোনও অবস্থাতেই Operating System-কে চার বা তার বেশি component-এ expand করবেন না।

আপনার analysis যত গভীরই হোক, যত কারণ, mechanism, relationship, factor বা process আবিষ্কৃত হোক—শেষ পর্যন্ত সেগুলিকে অবশ্যই Method, Architecture অথবা Operating Rules-এর উপযুক্ত অংশে map করতে হবে।

লক্ষ্য হলো Issue-এর remedy দেওয়া নয়, Issue-এর উপর opinion দেওয়া নয়, অথবা শুধু তার কারণ বলা নয়।

লক্ষ্য হলো দৃশ্যমান ফলাফলের নিচে কাজ করা সেই তিন-অঙ্গের অন্তর্নিহিত ব্যবস্থা উন্মোচন করা:

Method + Architecture + Operating Rules।
